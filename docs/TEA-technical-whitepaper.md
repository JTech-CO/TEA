## 1. 개요

### 1.1 정의

TEA는 AI 코딩 에이전트가 **컨텍스트 윈도를 소비하는 방식**을 규율하는 스킬이다. 코드 산출물의 크기가 아니라, 태스크 완료까지 컨텍스트를 통과하는 총 토큰량을 대상으로 한다.

### 1.2 명명

Token Engineering for Agents. "토큰 맥싱(token maxxing)"의 반대 개념으로, 한 태스크의 소비를 **차 한 잔 분량**으로 줄인다는 의미를 담는다.

은유는 슬로건이 아니라 설계 제약이다.

| 은유 | 설계 귀결 |
|---|---|
| 정해진 양 | 소비에 상한 개념이 존재 (v2 이후 구현) |
| 다시 따른다 | 초과 시 자동 진행이 아니라 사용자 판단 |
| 농축이 아니라 적량 | 압축 금지. 절제만 허용 (§7) |

세 번째 줄이 TEA의 성격을 규정한다. Ponytail이 "50줄을 한 줄로 바꿔놓는 시니어"라면, TEA는 **필요한 만큼만 따르고 멈추는 쪽**이다. 밀도를 높이는 것이 아니라 양을 줄인다.

### 1.3 비목표

- 소스 코드의 문자 수 감축 (§4.2에서 무효로 판정)
- 번들 크기 최적화 (빌드 도구의 영역)
- Ponytail의 기능 재구현 (§5에서 위임)
- 응답 품질 저하를 통한 출력 토큰 절감 (§9.3)

## 2. 문제 정의

### 2.1 관측

AI 코딩 에이전트에게 태스크를 주면, 실제 소비 토큰은 산출된 코드 크기와 상관관계가 약하다. 20줄짜리 결과물을 내기 위해 수만 토큰이 소비되는 경우가 흔하다.

소비의 실제 발생 지점은 다음과 같다.

```
세션 총 토큰 ≈ Σ(턴별 컨텍스트) + Σ(턴별 출력) + Σ(추론)
```

여기서 산출물 코드는 세 항 모두에서 소수 지분이다.

### 2.2 소비 구조 분해

| 항목 | 성격 | 1회 규모 | 반복성 |
|---|---|---|---|
| 코드 문자 수 | 산출물 | ~10² | 낮음 |
| 파일 전체 읽기 | 입력 | ~10⁴ | 높음 |
| 코드의 산문 재진술 | 출력 | ~10³ | 매 턴 |
| 전체 재작성 vs 부분 패치 | 출력 | 파일 크기 비례 | 편집마다 |
| 간접 참조 1 hop | 입력 | ~10³ | 탐색마다 |
| 잘못된 설계 결정 1회 | 복합 | ~10⁴ 이상 | 사고성 |

자릿수가 두 개 이상 벌어진다. 최적화 노력은 이 순서를 따라야 한다.

### 2.3 곱셈 구조

가장 중요한 구조적 사실은 다음이다.

```
총 토큰 ≈ (턴당 컨텍스트) × (턴 수)
```

**턴 수가 곱셈 계수**다. 턴당 컨텍스트를 10% 줄이면서 턴 수를 20% 늘리는 최적화는 순손실이다.

이 부등식이 TEA의 모든 규칙에 대한 승인 조건이 된다. 어떤 규칙도 재시도율을 높이면서 채택될 수 없다.

**실증 사례.** 출력 산문을 압축하는 스킬(caveman)은 단발 프롬프트 기준 출력 토큰을 평균 65% 줄인다. 그러나 동일 스킬을 실제 에이전트 세션에 투입한 대조 측정에서는 **총 토큰이 7% 증가**했고 비용과 시간도 함께 올랐다. 같은 조건에서 구현량을 줄이는 스킬(Ponytail)은 총 토큰 22%, 비용 20%, 시간 27%를 낮췄다.

| 개입 | 대상 | 단발 측정 | 에이전트 세션 총 토큰 |
|---|---|---|---|
| 산문 압축 | 표현 | 출력 −65% | **+7%** |
| 구현 축소 | 산출물 | LOC −80~94% | −22% |

앞항을 줄이고 뒷항을 늘리면 진다는 §2.3의 예측이 그대로 관측된다. TEA가 단발 벤치마크가 아닌 에이전트 루프에서 검증되어야 하는 이유이며, 단발 기준이었다면 산문 압축도 통과했을 것이다.

### 2.4 출력 토큰의 과소평가

코딩 세션에서 어시스턴트 출력 토큰의 상당 부분이 **방금 작성한 코드를 산문으로 다시 설명하는 데** 쓰인다. 사용자는 코드를 이미 볼 수 있으므로 이 재진술의 정보량은 0에 수렴한다.

**초안 정정.** 이 항목을 TEA의 차별 지점으로 기재했으나 사실과 다르다. 출력 토큰 규율은 이미 전용 도구(caveman)가 점유하고 있으며, 단발 기준 65% 감축이라는 실측치를 낸다. 다만 §2.3에서 보았듯 그 감축이 에이전트 세션의 총 토큰 감소로 이어지지는 않는다.

따라서 이 절의 결론은 둘로 갈린다.

- **출력 토큰이 크다**는 관측은 유효하다
- **그것을 줄이면 총 토큰이 준다**는 추론은 반증되었다

TEA는 이 영역을 정의역에서 제외한다(§6.4).

## 3. 비용 모델

### 3.1 계층 구분

소비를 세 계층으로 나눈다. 각 계층의 절감 성격이 다르다.

**계층 A — 일회성 절감**
산출물 자체의 크기. 한 번 줄이면 그것으로 끝난다.

**계층 B — 복리 절감**
존재하지 않는 코드는 이후 모든 턴의 읽기, diff, 테스트, 디버깅에서 반복 과금되지 않는다. Ponytail이 여기를 담당한다.

**계층 C — 계수 절감**
턴 수 자체를 줄인다. §2.3의 곱셈 구조상 효과가 가장 크다. 재시도 방지, 사전 확인, 방향 결정이 여기 속한다.

### 3.2 우선순위 도출

```
C  >  B  >>  A
```

TEA는 C를 주 담당으로, B의 프로세스 측면(읽기·편집 방식)을 부 담당으로 한다. A는 명시적 비목표다.

### 3.3 규모 감각

date picker 사례를 기준으로 삼는다. 404줄이 23줄이 된 케이스에서, 삭제된 380줄은 압축된 것이 아니라 애초에 불필요했던 의존성 래퍼·스타일시트·타임존 처리였다. 이것이 계층 B다.

같은 23줄을 12줄로 압축하면 계층 A에서 약 10²토큰을 얻는다. 계층 B 절감의 40분의 1 규모이며, 계층 C에서 재시도 1회를 유발하면 즉시 상쇄된다.

## 4. 기존 접근의 미커버 영역

### 4.1 미니파이어

esbuild, Terser 등은 계층 A만 처리하며, 그것도 빌드 산출물에 한정된다. 에이전트가 소비하는 토큰과 무관하다.

### 4.2 Code golf — 무효 판정

문자 수 압축은 계층 A에서 소액을 벌고 계층 C에서 대액을 잃는다. 근거는 셋이다.

**편집 앵커 실패.** 밀집 코드는 문자열 치환 기반 편집에서 고유 앵커 확보가 어렵다. 매칭 실패 1회의 비용(재읽기 + 재시도)이 압축으로 번 것의 수십 배다.

**diff 팽창.** 한 줄에 다중 로직이 결합되면 모든 변경이 그 줄 전체로 잡힌다. 부분 패치의 이점이 소멸한다.

**분포 이탈.** LLM은 관용적 코드에서 생성·수정 정확도가 가장 높다. 골프 인접 표현(`~~x`, 암묵적 전역, `eval`)은 학습 분포 밖이며, 정확도 저하가 재시도 턴으로 환원된다. 압축률과 정확도의 트레이드오프가 아니라 **양쪽이 동시에 나빠지는 구간**이다.

결론: 문자 압축은 TEA에서 금지 조항으로 격상한다(§7).

### 4.3 기존 생태계 지도

계층별로 이미 전용 도구가 존재한다. TEA의 정의역은 그 사이의 공백이다.

**Ponytail — 계층 B.** YAGNI를 에이전트 의사결정에 주입하여, 새 코드를 쓰기 전에 기존 코드·표준 라이브러리·네이티브 기능을 순서대로 검토하게 한다.

**caveman — 출력 표현.** 에이전트 발화를 압축한다. 코드는 바이트 단위로 보존하고 산문만 건드린다. Ponytail 측 문서도 양자를 "서로 다른 반쪽, 겹침 없음"으로 규정한다 — 하나는 말하는 것을, 하나는 만드는 것을 줄인다.

| 영역 | Ponytail | caveman | 비고 |
|---|---|---|---|
| 무엇을 쓸 것인가 | 담당 | — | |
| 무엇을 말할 것인가 | — | 담당 | 총 토큰 효과는 §2.3 참조 |
| **어떻게 읽을 것인가** | 미담당 | 미담당 | 계층 C 최대 항목 |
| **어떻게 편집할 것인가** | 부분 | — | 코드량만, 패치 방식 미담당 |
| **언제 확인할 것인가** | 미담당 | 미담당 | 재시도 방지 |
| **파일 수·참조 depth** | 미담당 | — | 오히려 분할 유인 가능 |

굵은 네 행이 공백이다.

마지막 행에 주의한다. Ponytail은 코드량을 지표로 삼으므로 파일 분할을 억제하지 않는다. 그러나 에이전트는 hop당 고정 읽기 비용을 내므로, 200줄 1파일이 40줄 5파일보다 저렴하다. **TEA와 Ponytail이 갈리는 유일한 실질 지점**이다.

### 4.4 결론

계층 C 전체와 계층 B의 프로세스 측면이 공백이다. TEA의 정의역이 여기다. 두 선행 도구가 "무엇을 만드는가"와 "무엇을 말하는가"를 가져갔고, **"어떻게 읽고 편집하고 판단하는가"가 비어 있다.**

**정의역 비충돌은 선행 사례가 자체 문서로 확인해 준다.** Ponytail은 자신의 규칙이 "최소 토큰"이었던 적이 없으며, 비용과 지연 감소는 사다리를 따르는 모델에서 나타나는 부수 효과라고 명시한다.

```
Ponytail :  토큰 = 부산물     (계층 B)
caveman  :  토큰 = 목적       (표현)
TEA      :  토큰 = 목적       (계층 C)
```

주의할 점은 목적 함수가 같은 쪽이 caveman이라는 것이다. 그리고 그쪽이 에이전트 세션에서 실패했다(§2.3). **TEA는 caveman의 목적을 공유하되 대상을 달리하는 설계**이며, 목적이 같다는 사실 자체가 경고다. 같은 실패를 반복하지 않는 유일한 보증은 §8.4의 통과 조건이다.

## 5. 아키텍처 제약

### 5.1 자기 회수 문제

토큰을 줄이는 스킬이 토큰을 소비한다. 손익분기를 통과해야 한다.

스킬의 로딩 구조는 3계층이다.

| 계층 | 내용 | 상주 여부 | 규모 |
|---|---|---|---|
| 1 | name + description | **항상** | ~100단어 |
| 2 | SKILL.md 본문 | 트리거 시 | 500줄 이내 권장 |
| 3 | 번들 리소스 | 필요 시 | 무제한 |

여기서 두 가지가 도출된다.

**항상 상주 비용은 작다.** 계층 1만 무조건 과금되며 ~100단어 규모다. 이 비용은 사실상 무시 가능하다.

**본문은 트리거당 과금된다.** 계층 2가 실질 비용이며, 손익분기 조건은 다음이 된다.

```
계층 2 토큰 < 해당 태스크에서의 절감 토큰
```

세션당이 아니라 **태스크당** 조건이라는 점이 중요하다. 초기 설계에서 "매 세션 주입"으로 오판했으나, 실제로는 트리거된 태스크에서만 발생한다. 제약이 완화된다.

### 5.2 태스크 크기 게이트는 이미 존재한다

스킬은 **에이전트가 스스로 처리 가능한 단순 작업에서는 발화하지 않는다.** 단발 질의나 1파일 편집에서는 설명이 완벽히 매칭되어도 트리거되지 않는다.

이는 TEA에 유리하게 작용한다. 자기 회수가 불가능한 짧은 태스크가 자동으로 배제되므로, **별도의 크기 게이트를 구현할 필요가 없다.** 초기 설계의 해당 항목을 삭제한다.

### 5.3 패키징과 트리거

반대 방향의 문제가 남는다. 스킬은 구조적으로 언더트리거 경향이 있으며, TEA가 필요한 상황은 정확히 **일상적 코딩 루프**다. "복잡하고 특수한 작업"에서만 발화하는 메커니즘과 어긋난다.

#### 5.3.1 언더트리거는 문구 문제다

> **[반증 기록 2026-08-18]** M1 실측에서 이 절의 전제가 반증됐다 — description 단독으로는 유기적
> 코딩 문항 발화율이 ≈47%에 수렴하며 게이트 도달 불가(통과 확률 ≈0.4%). 트리거 전략은 CLAUDE.md
> 로딩 어댑터 병용으로 개정됐다. 근거와 결정은 `harness/decisions/0010-trigger-adapter.md`.

초안은 이를 최대 아키텍처 위험으로 분류했으나, 선행 사례가 반증한다.

Ponytail은 스킬이 키워드 프롬프트뿐 아니라 모든 코딩 작업에서 발화하도록 개선하여, 코딩 작업 recall을 2/6에서 6/6으로 끌어올렸다. 정밀도는 유지되었다. **패키징 변경이 아니라 description 수정으로 달성했다.**

채택된 전략은 셋으로 분해된다.

| 요소 | 내용 |
|---|---|
| 정의역 전체 열거 | 작성·추가·리팩터링·수정·리뷰·설계·의존성 선택을 명시 |
| 키워드 병기 | 사용자가 쓸 법한 표현을 함께 나열 |
| 비적용 대상 명시 | 일반 지식, 산문, 번역, 요약 등을 배제해 정밀도 방어 |

여기에 본문 지속성 장치가 더해진다. Ponytail 본문은 매 응답에서 활성 상태를 유지하고 불확실할 때도 유지하며 명시적 해제 문구로만 꺼진다고 선언한다. **트리거 기반 스킬을 준상시로 만드는 방식**이다.

TEA의 정의역도 코딩 작업이므로 동일 전략이 그대로 적용된다. 따라서 언더트리거는 아키텍처 결정 사항이 아니라 문구 튜닝 사항으로 강등한다.

#### 5.3.2 그럼에도 플러그인이 최종형인 이유

상시성은 스킬로 확보 가능하지만, 다음 셋은 플러그인이어야만 가능하다.

**주입 계층 일치.** Ponytail 플러그인은 매 LLM 턴 직전에 활성 모드를 주입하며, 호스트에 따라 시스템 프롬프트 변환 훅으로 룰셋을 주입한다. TEA가 스킬 단독이면 주입 시점이 어긋난다 — Ponytail은 턴 시작 시스템 계층, TEA는 대화 중간이다. §4.3의 파일 분할 충돌에서 우선순위 중재가 필요한데, 계층이 다르면 중재 자체가 불가능하다. 후발 주입인 TEA가 의도치 않게 Ponytail을 덮을 위험도 있다.

**모드 연동.** Ponytail은 lite / full(기본) / ultra 강도를 슬래시 커맨드로 전환한다. TEA도 강도가 필요하며, 플러그인이면 동일 UX를 제공하는 데 더해 **Ponytail 모드를 읽어 연동**할 수 있다. 스킬은 슬래시 커맨드를 등록하지 못하므로 연동 자체가 성립하지 않는다.

**벤치마크 결정성.** §8.2의 C군이 확률적으로 발화하면 일부 C 실행이 실제로는 B 실행이 된다. C − B 측정이 오염된다. 플러그인 주입은 결정적이다.

#### 5.3.3 구조 결론

선행 사례의 구조를 그대로 채용한다. Ponytail은 에이전트 이식 가능한 스킬 배포판이며, `skills/`가 핵심 동작을 담고 호스트별 파일은 로딩 어댑터 역할만 한다.

```
행동 → 스킬        (이식 가능, 호스트 무관)
로딩 → 플러그인    (호스트별 어댑터, 커맨드·모드·훅)
```

스킬 대 플러그인은 양자택일이 아니다. **TEA도 2층으로 간다.**

전환 시점은 §10.4에서 정한다. 1~3단계는 스킬 + 공격적 description으로 규칙만 검증하고, 커맨드가 필요해지는 4단계에서 플러그인 어댑터를 추가한다. 어댑터 유지보수 비용을 규칙 확정 이후로 미루는 순서다.

### 5.4 규칙 표현의 딜레마

스킬 작성 원칙은 **왜 중요한지를 설명하라**고 권한다. 근거 없는 명령형 나열은 준수율이 낮기 때문이다.

이것이 토큰 최소화와 정면 충돌한다.

```
"파일 전체를 읽지 말 것"                        → 짧음, 준수율 낮음, 과긴축 위험
"읽기는 컨텍스트의 최대 소비 항목이므로, 위치를
 특정한 뒤 범위만 읽는다. 전체 읽기는 구조 파악이
 필요할 때만 정당하다."                          → 김, 준수율 높음, 판단 가능
```

**해결: 근거를 축당 1회만 제시한다.** 4개 축 각각에 2~3문장의 근거를 두고, 개별 규칙은 명령형으로 짧게 쓴다. 근거를 규칙마다 반복하지 않는다.

### 5.5 Ponytail과의 공존

**중복 주입 위험.** 양쪽 모두 "적게"를 지시하므로 겹쳐 넣으면 과소구현 압력이 이중으로 걸린다.

- TEA는 구현 최소화 규칙을 **싣지 않고 위임**한다
- Ponytail 미설치 시에만 최소 스텁(네이티브 우선 1줄)을 활성화
- 불가침 목록은 Ponytail의 것을 승계한다 — 검증, 예외 처리, 보안, 접근성
- §4.3 마지막 행(파일 수·depth)만 TEA가 독자적으로 규정한다

**모드 연동(4단계 이후).** Ponytail은 lite / full / ultra 강도를 가진다. TEA도 대응 강도를 두되, 독립 설정이 아니라 **Ponytail 모드를 읽어 따라가는 종속 설정**을 기본값으로 한다. 사용자가 강도 개념을 두 번 학습하지 않게 하고, 두 스킬이 서로 다른 강도로 걸려 규칙이 엇갈리는 상황을 방지한다. 독립 지정은 명시적 오버라이드로만 허용한다.

**중재 조항.** §4.3 마지막 행에서 양측 지침이 충돌할 경우 TEA가 우선한다. 파일 수와 참조 depth는 계층 C 비용이며, Ponytail의 지표(코드량)에는 계상되지 않기 때문이다. 이 조항은 양측이 같은 주입 계층에 있을 때만 실효를 가진다(§5.3.2).

## 6. 규율 축

**3개 축**으로 분해한다. 각 축은 §3.1의 계층에 대응한다. 초안의 4번째 축(SAY)은 §6.4의 근거로 제거했다.

### 6.1 사다리

행동 전 통과 순서. 첫 통과 지점에서 멈춘다.

```
1  추가 컨텍스트가 필요한가          → 아니면 즉시 실행
2  최소 단위로 특정 가능한가         → 위치 검색 우선
3  편집 범위가 확정되었는가          → 아니면 확정 먼저
4  최소 패치로 가능한가              → 전체 재작성은 구조 변경 시만
```

3번이 핵심이다. §2.3에 의해 **THINK 축이 READ 축보다 우선순위가 높다.**

**사다리 자체의 비용.** 선행 사례는 사다리를 숙고하는 데 추론 토큰을 쓰는 모델에서 총 소비가 역전될 수 있음을 보고한다(GPT-5.5). 사다리 단계를 늘리는 것은 무료가 아니다. 초안의 5단계를 4단계로 줄인 것은 SAY 축 제거의 결과이자, 이 위험에 대한 완화이기도 하다. **단계 추가는 §8.5의 기여도 측정을 통과한 경우에만 허용한다.**

### 6.2 READ

> 근거: 파일 읽기는 입력 토큰의 최대 항목이며, 대부분의 읽기가 실제 필요 범위를 크게 초과한다.

- 위치 검색으로 대상을 특정한 뒤 범위만 읽는다
- 전체 읽기는 구조 파악이 목적일 때만 정당하다
- 동일 파일 재읽기 금지. 편집 후 검증은 예외
- 디렉토리 탐색 depth에 상한을 둔다

### 6.3 WRITE

> 근거: 편집 방식이 출력 토큰과 이후 턴의 읽기 비용을 동시에 결정한다.

- 부분 패치 우선. 전체 재작성은 구조 변경에 한정
- 편집 앵커는 고유하되 최소 폭
- 파일 분할 억제 — hop당 고정 비용이 줄 밀도보다 비싸다
- 미요청 산출물 금지 — 테스트, README, 예제, 설정 파일
- 방금 작성한 코드를 산문으로 재진술하지 않는다

마지막 항목은 스타일 규칙이 아니라 **중복 삭제 규칙**이다. 사용자는 diff를 이미 볼 수 있으므로 재진술의 정보량이 0이다. §7.1 기준선의 "의미가 없는 것을 안 쓴다"에 해당하므로 WRITE 축에 남긴다.

### 6.4 SAY 축 제거

초안은 출력 표현을 4번째 축으로 두었다. 제거한다.

**근거 1 — 정의역 중복.** 이 영역은 caveman의 전용 정의역이며, 단발 기준 65% 감축이라는 실측치를 가진 전용 도구가 이미 존재한다. §5.5의 위임 원칙을 적용하면 TEA가 다룰 이유가 없다.

**근거 2 — 반증된 가설.** 더 중요한 이유다. 해당 접근은 에이전트 세션에서 총 토큰을 **7% 증가**시켰다(§2.3). 정의역이 비어 있었더라도 채택할 근거가 없다.

**근거 3 — 코어 경량화.** 축이 3개로 줄면 §5.1의 계층 2 본문이 가벼워지고 §6.1의 사다리도 한 단계 짧아진다.

**남기는 것.** "코드 재진술 금지" 한 줄만 WRITE 축으로 이관한다(§6.3). 스타일 압축이 아니라 중복 삭제이므로 caveman과 성격이 다르고 충돌하지 않는다.

**병용 권고.** 출력 토큰 감축을 원하는 사용자는 caveman을 별도 설치하면 된다. 다만 §2.3의 측정 결과를 근거로, **TEA는 caveman 병용을 권고하지 않는다.** 총 토큰을 지표로 삼는 한 병용은 순손실이다. 단발 질의 위주 사용자에게는 유효할 수 있으나 그 구간은 TEA의 정의역이 아니다(§5.2).

### 6.5 THINK

> 근거: 재시도 1회가 다른 축의 절감분 수십 회를 상쇄한다. 턴 수는 곱셈 계수다.

- 되돌리기 비용이 확인 비용보다 크면 확인을 먼저 한다
- 설계 분기는 편집 착수 전에 해소한다
- 불확실한 상태에서 추측 편집을 하지 않는다

## 7. 경계 조항

### 7.1 기준선

> **같은 의미를 더 짧게 쓰는 것은 금지. 의미가 없는 것을 안 쓰는 것은 권장.**

### 7.2 금지

- 식별자 축약
- 문자 단위 압축, 의미 밀도 증가
- 관용구 이탈 표현 (`~~x`, 암묵적 전역, `eval`, `with`)
- 한 줄에 다중 로직 결합

### 7.3 권장

- 코드를 그대로 옮긴 주석 삭제
- 추론 가능한 타입 주석 삭제
- 1회용 중간 변수 제거
- 도달 불가능한 분기의 방어 코드 제거

### 7.4 불가침

Ponytail 승계. 어떤 규율 축도 다음을 축소하지 않는다.

- 신뢰 경계 검증
- 예외 처리 및 데이터 손실 방지
- 보안
- 접근성

### 7.5 존재 이유

이 조항이 없으면 지표가 LOC로 미끄러지는 순간 골프가 자동 발생한다. Goodhart의 법칙에 대한 구조적 방어다.

## 8. 측정 방법론

### 8.1 지표

**주지표**
- 태스크 완료까지 총 토큰 (input + output + reasoning)
- 턴 수

**부지표**
- 재시도율
- 도구 호출 실패율
- 트리거율 (§5.3 전환 판단용)

**제외**
- LOC. §7.5의 이유로 지표에서 배제한다.

### 8.2 비교군

표준 스킬 평가는 with-skill / without-skill 2군이지만, TEA는 3군이 필요하다.

```
A  베이스라인 (스킬 없음)
B  Ponytail 단독
C  Ponytail + TEA        ← 목표 구성
```

**C − B가 TEA의 순기여다.** TEA 단독 측정은 의미가 없다. Ponytail이 계층 B를 처리한 뒤에 남는 계층 C를 재는 것이 TEA의 정의이기 때문이다.

A는 Ponytail 대비 TEA의 상대 규모를 보기 위한 참조군으로만 둔다.

### 8.3 계측 확보

토큰 및 소요 시간은 서브에이전트 실행 완료 시 `total_tokens` / `duration_ms`로 회수 가능하다. 이 데이터는 완료 통지 시점에만 확보되므로 즉시 저장해야 한다.

집계는 기존 벤치마크 스크립트를 활용하면 pass_rate·time·tokens를 평균 ± 표준편차와 델타까지 산출할 수 있다. **별도 계측 하네스를 구축할 필요가 없다.**

3군 구조는 표준 스크립트의 2군 가정에서 벗어나므로, 이 부분만 확장이 필요하다.

**태스크셋 재사용.** 선행 사례가 공개한 방법론을 그대로 채용한다.

| 항목 | 채용 내용 |
|---|---|
| 대상 레포 | `tiangolo/full-stack-fastapi-template` (실제 FastAPI + React) |
| 태스크 | 12개 feature 티켓 |
| 반복 | n = 4 |
| 실행 | headless 에이전트 세션 |
| 채점 | git diff 기반 |

**변경점은 지표 하나뿐이다.** 선행 사례는 diff의 LOC를 주지표로 삼았으나, TEA는 §8.1에 따라 LOC를 배제하고 총 토큰과 턴 수를 본다. 태스크셋과 실행 하네스는 검증된 것을 재사용하고, 스코어링만 교체한다.

이 선택은 이중 이득이 있다. 하네스 구축 비용을 없애고, B군(Ponytail 단독) 수치를 선행 측정치와 대조해 재현성을 검증할 수 있다. 재현이 안 되면 환경 문제이지 TEA 문제가 아님을 먼저 확인할 수 있다.

### 8.4 통과 조건

> **[반증 기록 2026-08-19]** 이 게이트가 설계 목적대로 작동해 TEA 자신을 걸러냈다. 3군 288트라이얼
> (sonnet-5·opus-5, n=48/셀) 실측에서 C−B = +17~19%로 두 모델 모두 조건 ②③ 미달 — 채택 불가.
> 원인은 규칙 내용이 아니라 스킬 전달 라운드(호출 콜의 기저 컨텍스트 재과금 + 본문 주입 턴)이며,
> 주입형 전달로 바꿔도 판정 전환 확률 ≤1%로 산출됐다. §2.3의 곱셈 구조 경고가 TEA 자신에게
> 적용된 결과다. 상세: `harness/phases/M6.md`, 데이터: `bench/results/`.

전부 충족해야 채택한다.

1. 기능 동등성 유지
2. 총 토큰 감소 (C < B, 통계적으로 유의)
3. **턴 수 비증가**
4. 재시도율 비증가
5. 불가침 항목 미훼손

3번과 4번이 가드다. IO 긴축이 재시도를 유발하는 경우가 여기서 걸린다.

### 8.5 규칙별 기여도

전체 스킬의 순효과가 양수여도 개별 규칙 중 음수 항목이 존재할 수 있다. 규칙을 늘리기 전에 개별 기여도를 측정하고 음수 항목을 제거한다.

**지표 확정 전에는 규칙을 늘리지 않는다.** 측정 없이 추가된 규칙은 되돌릴 근거도 없이 누적된다.

### 8.6 분산 관리

에이전트 실행은 분산이 크다. 단일 실행 비교는 신뢰할 수 없다. 태스크당 최소 3~4회 반복하고 평균과 표준편차를 함께 본다. 표준편차가 델타보다 크면 결론을 내지 않는다.

## 9. 위험 분석

### 9.1 IO 과긴축 — 최대 위험

**경로:** 읽기 억제 → 컨텍스트 부족 → 잘못된 편집 → 재시도 폭증 → 총 토큰 증가

이 스킬은 잘 만들면 절감, 잘못 만들면 증가하는 구조이며 중간값이 없다.

**완화**
- THINK 축이 READ 축보다 우선한다는 순서를 사다리에 명시
- 규칙 문구를 "읽지 마라"가 아니라 "정확히 필요한 것만 읽어라"로 표현
- §8.4의 3·4번 통과 조건으로 차단

### 9.2 자기 회수 실패

**완화:** §5.2에 의해 구조적으로 대부분 해소. 잔존 위험은 계층 2 본문 비대화이므로, 본문을 사다리 + 3축 규칙 + 축당 근거로 제한하고 사례집은 계층 3으로 내린다.

### 9.3 사다리의 추론 비용 — 신규

**경로:** 사다리 단계 증가 → 매 행동마다 숙고 → 추론 토큰 증가 → 총 토큰 상쇄

선행 사례는 사다리를 숙고하는 데 추론 토큰을 쓰는 모델에서 총 소비가 역전되는 사례를 보고한다(GPT-5.5). 사다리는 무료가 아니며, 규율 축 자체가 비용을 발생시킨다.

TEA는 선행 사례보다 사다리가 짧지만(4단계 대 7단계), 판단 대상이 매 도구 호출이라 **발동 빈도가 더 높다.** 위험은 오히려 크다.

**완화**
- 단계 추가는 §8.5 기여도 측정 통과 시에만 허용
- 총 토큰 지표에 추론 토큰을 포함해 계측(§8.1) — 이 항목을 빼면 위험이 측정에서 사라진다
- 모델별 편차를 전제하고, 최소 2개 모델에서 검증

### 9.4 설명 부족 — 축소 개정

초안의 "SAY 과적용"은 SAY 축 제거(§6.4)로 대부분 소멸했다. 잔존 경로는 하나다.

**경로:** 코드 재진술 금지 → 사용자가 변경 내용 파악 실패 → 되묻는 턴 발생 → 순손실

**완화:** §6.3의 재진술 금지는 diff로 확인 가능한 내용에만 적용한다. 사용자 판단이 필요한 정보(설계 근거, 남은 선택지, 부작용)는 대상이 아님을 규칙에 명시한다.

### 9.5 목적 함수 동형성 — 신규, 최대 개념적 위험

**경로:** 토큰을 목적으로 삼음 → 측정 가능한 것을 최적화 → 측정 밖의 비용으로 전가 → 총량 증가

§4.4에서 확인했듯 TEA와 목적 함수가 같은 것은 caveman이며, 그쪽이 에이전트 세션에서 실패했다. Ponytail은 토큰을 목적으로 삼지 않았고 성공했다.

이는 우연이 아니라 구조적 가능성이 있다. **"토큰을 줄여라"는 지시 자체가 측정되지 않는 축으로 비용을 밀어내는 경향**을 가질 수 있다. §7.5의 Goodhart 방어가 코드 골프만이 아니라 TEA 자신에게도 적용된다.

**완화**
- §8.4 통과 조건 5개 전부를 게이트로 유지. 총 토큰 감소 단독으로는 채택하지 않는다
- 규칙 문구에서 "토큰을 줄여라"를 직접 쓰지 않는다. 각 규칙은 행동 수준으로 기술하고, 토큰은 결과 지표로만 둔다
- 정기적으로 B군 대비 기능 동등성을 재확인한다

### 9.6 과소 구현

Ponytail에서 상속되는 위험. **완화:** §7.4 불가침 목록.

선행 측정은 이 위험이 실재함을 보인다. "YAGNI + 한 줄로" 류의 단순 지시는 안전 가드 항목에서 95%로 떨어졌고, 사다리 기반 접근만 100%를 유지했다. **지시를 짧게 만들수록 안전 항목이 먼저 희생된다는 직접 증거**이며, §7.2의 골프 금지와 §7.4 불가침을 동시에 뒷받침한다.

### 9.7 규칙 충돌

**완화:** §5.5 위임 구조. TEA는 구현 판단에 개입하지 않는다.

### 9.8 언더트리거

§5.3.1에 의해 **아키텍처 위험에서 문구 튜닝 과제로 강등한다.** 선행 사례가 패키징 변경 없이 description만으로 recall 2/6 → 6/6을 달성했다.

**완화:** 정의역 열거 + 키워드 병기 + 비적용 명시의 3요소 적용, 본문 지속성 선언 삽입. 트리거율을 부지표로 계측하되, 미달 시 대응은 패키징 전환이 아니라 문구 재작성이다.

**잔존 위험:** 정밀도 저하. 트리거 범위를 넓히면 비코딩 작업에서의 오발화가 늘 수 있다. recall과 precision을 함께 계측한다.

## 10. 범위 결정

### 10.1 티컵 예산 유보

행동 카운트 기반 소비 상한과 리필 확인 메커니즘을 v1에서 제외한다.

**근거**

**벤치마크 오염.** 임계값 초기치는 근거 없는 추측이며 튜닝하려면 벤치마크가 필요하다. 예산을 v1에 포함하면 그 벤치마크 자체가 오염되어, C군 결과 악화 시 원인 분리가 불가능하다.

**자기 모순.** 리필 확인은 정의상 턴을 증가시킨다. §8.4의 3번 통과 조건을 TEA 자신의 메커니즘이 위반한다.

**실패 양상 차이.** 규율 축의 실패는 완만한 열화(토큰 소폭 증가)이지만, 예산의 실패는 급격한 실패(작업 중단, 사용자 개입 요구)다. v1에 급격한 실패 모드를 도입할 이유가 없다.

**전제 조건 미충족.** 예산의 주 효용은 폭주 세션 차단이다. 대상 사용 환경에서 20턴 이상 오방향 진행 사고가 거의 관측되지 않으므로, 기대 효용이 낮다.

### 10.2 계수와 차단의 분리

예산은 두 기능의 묶음이다. 전자만 남긴다.

| 기능 | 비용 | v1 |
|---|---|---|
| 계수 — 읽기·편집·턴 수 추적 | 거의 0 | 포함 (사후, 축소) |
| 차단 — 중단 후 리필 요청 | 높음, 위험 동반 | 제외 |

**토큰·비용 집계는 위임한다.** caveman이 `/caveman-stats`로 실제 세션 토큰 사용량과 누적 절감액을 제공하며, 세션 로그를 파싱하는 방식이다. 동일 기능을 재구현할 이유가 없다.

TEA가 남기는 것은 **분포**다. 토큰 총량이 아니라 그것이 읽기·편집·턴 어디로 갔는지가 §8.5 기여도 측정의 입력이 된다. 위임 후 남는 정의역이 좁아지므로, 감사 기능은 4단계 이후로 미루고 v1에서는 벤치마크 하네스(§8.3)가 그 역할을 대신한다.

사후 감사 방식은 인플라이트 추적보다 정확하다. 에이전트가 긴 세션에서 자기 도구 호출을 실시간으로 정확히 세는 것은 신뢰도가 낮다.

부수 효과로, 누적된 소비 분포가 v2 임계값의 실증 근거가 된다.

### 10.3 명명 정합성

예산 제외로 "차 한 잔" 은유가 장식이 된다는 우려가 있으나, 반대다. **이름이 아키텍처를 끌고 가는 것이 더 큰 위험이다.**

은유의 본체는 절제의 철학이지 특정 메커니즘이 아니며, 규율 축만으로 충족된다. 사후 감사가 "이번 잔은 얼마나 들었는가"를 제시하므로 서사도 유지된다.

### 10.4 단계

| 단계 | 형태 | 내용 | 완료 조건 |
|---|---|---|---|
| 1 | 스킬 | 규율 축 3개 + 공격적 description | 초안 완성, 트리거 recall 목표 도달 |
| 2 | 스킬 | 3군 벤치마크 하네스 | §8.1 지표 산출 |
| 3 | 스킬 | 규칙별 기여도 측정, 음수 항목 제거 | §8.4 전 조건 통과 |
| 4 | **플러그인** | 사후 감사 커맨드, 강도 조절, Ponytail 모드 연동 | 어댑터 동작 확인 |
| 5 | 플러그인 | 크로스 에이전트 이식 | 1~4 안정화 후 |

**1~3단계는 스킬로 진행한다.** 규칙이 확정되기 전에 어댑터 유지보수 비용을 내지 않기 위함이며, §5.3.1에 의해 이 구간에서도 상시성은 description으로 확보된다.

**4단계에서 플러그인으로 전환한다.** 전환 트리거는 트리거율 미달이 아니라 **커맨드 필요 시점**이다. 강도 조절과 Ponytail 모드 연동이 여기서 처음 필요해진다(§5.3.2).

크로스 에이전트는 유보한다. 다중 에이전트 지원은 초기 단계에서 유지보수 부담만 증가시키며, 규칙이 확정되기 전에는 이식할 대상 자체가 불안정하다. 단, 1~3단계의 산출물을 `skills/`에 두고 호스트 의존 요소를 섞지 않으면 5단계 이식 비용이 크게 줄어든다(§5.3.3).

## 11. 미해결 과제

설계 백서 착수 전 결정이 필요한 항목이다.

### 11.1 해소된 항목

**기능 중복 검증 — 완료.** Ponytail의 5개 커맨드를 확인한 결과 §10.2와의 중복은 없다.

| 커맨드 | 대상 | TEA와의 관계 |
|---|---|---|
| `/ponytail-review` | 현재 diff의 과잉 구현 | 무관 (코드 대상) |
| `/ponytail-audit` | 레포 전체의 과잉 구현 | 무관 (코드 대상) |
| `/ponytail-debt` | 미룬 단축의 원장 | 무관 |
| `/ponytail-gain` | 벤치마크 임팩트 스코어보드 | 무관 (실측 아님) |

전부 **코드**를 대상으로 하며, TEA의 감사는 **세션 소비**를 대상으로 한다.

**단, 다른 곳에서 중복이 확인되었다.** `/caveman-stats`가 실제 세션 토큰 사용량과 누적 절감액을 세션 로그 파싱으로 제공한다. §10.2를 그에 맞게 축소 개정했다.

**패키징 방식 — 완료.** §5.3.3에서 2층 구조로 확정.

### 11.2 잔존 항목

1. **description 문구** — 언더트리거 대응의 1차 수단(§5.3.1). 정의역 열거·키워드 병기·비적용 명시의 3요소를 TEA 정의역으로 재작성하고, 트리거 평가셋으로 recall을 측정한다. 목표치는 선행 사례 수준(6/6)이되 정밀도 저하가 없어야 한다
2. **Schema-Hub 14섹션 포맷과의 관계** — 계층 2 본문을 축약 포맷으로, 전체 14섹션을 계층 3의 `references/spec.md`로 분리하는 예외 처리 승인 필요
3. **서브에이전트 스코프** — 신규. Ponytail은 서브에이전트에도 룰셋을 주입하며 정규식으로 스코프를 조절한다(예시 용도: 읽기 전용 탐색 에이전트에서 제외). **TEA의 READ 축은 정확히 그 에이전트에 걸어야 하므로 스코프 방향이 반대다.** 별도 정책이 필요하다
4. **Ponytail 감지 방식** — 미설치 시 스텁 활성화 조건. 모드 파일(`~/.config/ponytail/config.json`) 또는 환경 변수 존재 여부로 판정 가능한지 확인
5. **모델 커버리지** — 신규. §9.3에 따라 최소 2개 모델에서 검증해야 한다. 선행 사례는 Haiku 4.5로 측정했고 GPT-5.5에서 역전을 보고했다. 검증 모델 조합을 확정해야 한다
6. **브레비티 문헌 검토** — 신규. 간결 제약이 특정 벤치마크 정확도를 개선했다는 보고(arXiv 2604.00025)가 있다. §4.2의 "압축은 정확도를 떨어뜨린다"는 주장과 대립할 수 있으므로, 출력 간결성과 코드 압축을 구분해 검토해야 한다

## 부록 C. 후속 연구 가설 — 장기·대형 세션 (v0.4 신설)

> v1 반증(§8.4 각주, `harness/phases/M6.md`) 후 사용자 결정(2026-08-19)으로 기록한다.
> 이것은 확증된 방향이 아니라 **반증 가능한 가설**이며, v1과 같은 게이트 규율로만 검증한다.

### C.1 이 가설이 존재하는 이유

v1 반증의 기전은 태스크셋의 성격과 결합되어 있다.

- 측정 태스크는 B군 평균 11.9~12.6턴의 **단기 세션**이었다. 이 구간에서 규율이 회수할 계층 C 낭비 자체가 작다 — Ponytail 위의 세션은 이미 알뜰했다.
- TEA의 비용은 **세션당 고정**이다. 전달 라운드가 기저 컨텍스트 1회분(실측 25~34k)을 재과금하며, 단기 세션에서 이 고정비는 총비용의 8~10%로 몇 천 토큰 규모의 규율 절감을 항상 압도한다.
- 규율 효과 자체는 실재했다 — sonnet 중복 읽기 0.42→0.17, 읽기 수 감소, 기능 동등성 100% 유지. 문제는 효과의 존재가 아니라 **고정비 대비 회수 규모**다.

### C.2 가설

**H1 (규모 가설).** 전달 비용은 세션 길이에 대해 상수이고, 계층 C 낭비(중복 읽기·재시도·방향 상실)는 세션 길이·컨텍스트 크기에 대해 초선형으로 누적된다. 따라서 손익분기 세션 규모 L\*가 존재하며, v1 태스크셋은 L\* 미만 구간에 있었다.

**H2 (전달 가설).** 주입형 전달(시스템 계층 주입, 스킬 호출 턴 제거)에서 고정비는 본문 캐시 생성 ~1k 수준으로 떨어진다. v1 데이터의 반사실 추정에서도 C′−B 중앙값은 0 부근이었다 — 장기 세션에서는 부호가 음수로 넘어갈 여지가 있다.

### C.3 v1 데이터가 주는 단서 (약한 증거 — 확증 아님)

- 델타는 꼬리 주도였다: 평균 +54~76k vs 중앙값 +23~30k. 세션이 길수록 분산이 커졌고 n=4로는 분리되지 않았다(RUNBOOK #13).
- 최대 손실 트라이얼(be-archive, 2.69M tok·57턴)은 동시에 낭비가 가장 컸던 세션이다 — 규율이 먹힐 여지와 실패할 여지가 함께 커지는 구간이 존재한다.
- 이 단서들은 방향을 시사할 뿐이다. v1에서 H1을 지지하는 유의한 부호 전환은 관측되지 않았다.

### C.5 반증 조건 (사전 등록)

장기·대형 세션에서도 주입형 전달로 C′−B ≥ 0이면, **"계층 C를 규율 텍스트로 회수한다"는 접근 자체를 폐기한다.** 그 경우 남는 경로는 규율의 도구화뿐이다 — 규칙을 모델에게 읽히는 대신 하네스가 기계적으로 집행하는 것(예: R3 중복 읽기는 클라이언트 캐시로, W2 앵커 폭은 편집 도구의 재시도 로직으로, T3은 편집 전 강제 상태 확인으로). 텍스트 규율의 비용은 컨텍스트에 계상되지만 도구 집행의 비용은 계상되지 않는다.
