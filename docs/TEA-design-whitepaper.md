# TEA — Token Engineering for Agents

## 설계 백서 v0.1

| | |
|---|---|
| 문서 단계 | 설계 백서 (하네스 팩 선행) |
| 선행 문서 | 기술 백서 v0.3 |
| 대상 | 1단계 산출물 명세 + 2~3단계 검증 절차 |
| 확정 범위 | 규율 축 3개, 2층 패키징, 티컵 예산 v1 제외 |

---

## 1. 문서의 역할

기술 백서가 **무엇을 왜**를 확정했다. 이 문서는 **무엇을 어떻게 만들 것인가**를 확정한다.

```
기술 백서 v0.3   →  이 문서       →  하네스 팩      →  구현
   문제·근거        산출물 명세       템플릿·프롬프트     SKILL.md
```

기술 백서에서 그대로 승계하며 이 문서에서 재논증하지 않는 것.

- 계층 A/B/C 비용 모델과 우선순위 `C > B >> A`
- 곱셈 구조 `총 토큰 ≈ (턴당 컨텍스트) × (턴 수)`
- 규율 축 3개 (READ / WRITE / THINK)
- 2층 패키징 (행동=스킬, 로딩=플러그인)
- 금지 조항과 불가침 목록

이 문서가 새로 정하는 것: 파일 구조, 규칙 카탈로그와 ID 체계, description 문안, 평가셋 설계, 벤치마크 절차, 채택 게이트 운용 방식.

### 1.1 자기 적용 원칙

TEA 문서는 TEA 규칙을 위반하지 않는다. 기술 백서 §5.1의 자기 참조 테스트를 이 문서에도 적용한다. 구체적으로 규칙 카탈로그(§4)는 근거를 축당 1회만 서술하고 규칙마다 반복하지 않는다.

## 2. 산출물 구조

### 2.1 1단계 트리

```
tea/
├── SKILL.md                    계층 2. 트리거 시 로드
├── references/
│   ├── read.md                 READ 축 판단 사례
│   ├── write.md                WRITE 축 판단 사례
│   ├── think.md                THINK 축 판단 사례
│   ├── boundaries.md           금지·불가침 사례집
│   └── spec.md                 Schema-Hub 14섹션 전문
└── evals/
    ├── trigger.json            트리거 평가셋
    └── tasks.json              벤치마크 태스크셋 참조
```

`references/`는 SKILL.md에서 파일명과 로드 조건만 언급하고 본문은 싣지 않는다. `evals/`는 배포 대상이 아니며 저장소에만 둔다.

### 2.2 토큰 예산

| 계층 | 대상 | 목표 | 상한 | 과금 |
|---|---|---|---|---|
| 1 | frontmatter description | 90~120단어 | 150단어 | 상시 |
| 2 | SKILL.md 본문 | 600~900토큰 | 1,200토큰 | 트리거당 |
| 3 | references/ 각 파일 | 제한 없음 | — | 필요 시 |

계층 2 상한의 근거는 회수 조건이다. 회피한 전체 파일 읽기 1회가 10⁴ 규모(기술 백서 §2.2)이므로, 1,200토큰은 태스크당 읽기 1회만 줄여도 회수된다. 500줄 권장선 대비 넉넉한 여유가 있으나, §9.3의 사다리 추론 비용 때문에 규칙 수 자체를 늘리지 않는다.

### 2.3 4단계 추가 트리 (사전 명세)

```
tea/
├── .claude-plugin/
│   └── plugin.json             마켓플레이스 매니페스트
├── hooks/
│   └── hooks.json              턴 전 주입, 모드 추적
└── commands/
    ├── tea.md                  강도 전환
    └── tea-audit.md            세션 소비 분포
```

1~3단계에서는 생성하지 않는다. 다만 1단계 산출물이 `skills/` 상당 위치에 호스트 의존 요소 없이 놓이도록 유지해, 전환 시 어댑터만 추가하면 되게 한다.

## 3. 트리거 명세

### 3.1 설계 원칙

기술 백서 §5.3.1의 3요소를 그대로 적용한다.

| 요소 | 목적 |
|---|---|
| 정의역 전체 열거 | recall 확보 |
| 키워드 병기 | 사용자 표현 매칭 |
| 비적용 대상 명시 | precision 방어 |

여기에 본문 지속성 선언을 더해 트리거 후 드리프트를 막는다.

### 3.2 description 초안

```
Disciplines how the agent spends context: locate before reading, patch
instead of rewriting, and resolve uncertainty before editing rather than
after. Cuts total session cost by removing wasted reads, whole-file
rewrites, and retry loops. It does not shorten code or prose — it reduces
how much work the agent does to get the same result.

Use on ANY multi-step coding task: navigating or reading a codebase,
editing across files, debugging, refactoring, reviewing, investigating a
failure, or planning a change. Also use whenever the user mentions "tea",
"context budget", "too many tokens", "this session is expensive", "this
is slow", or complains that the agent keeps re-reading files, rewrites
whole files, or goes in circles.

Do NOT use for non-coding requests (prose, translation, summaries,
general knowledge), and never as an instruction to shorten code,
compress identifiers, or golf.
```

**설계 의도**

1문단이 정의역을 규정하되 마지막 문장에서 골프와 명시적으로 분리한다. 기술 백서 §9.5의 목적 함수 동형성 위험에 대한 1차 방어이며, description 단계에서 오해를 차단한다.

2문단이 recall을 담당한다. 코딩 작업 유형 7종과 사용자 표현 6종을 병기했다. "navigating or reading a codebase"를 첫 항목에 둔 것은 READ 축이 최대 절감 항목이기 때문이다.

3문단이 precision을 담당한다. 비코딩 배제에 더해 골프 지시로의 오용을 명시적으로 금지한다.

**미확정.** "tea"는 일반 명사라 오발화 가능성이 있다. §5의 평가셋에서 precision 저하가 관측되면 `/tea` 커맨드 도입(4단계) 전까지 이 키워드를 제거한다.

### 3.3 본문 지속성 선언

SKILL.md 본문 첫 블록에 배치한다.

```
Active on every turn of a coding task. Do not drift back to
read-everything, rewrite-everything defaults mid-session. Still active
when uncertain. Off only on explicit "stop tea" / "normal mode".
```

## 4. 규칙 카탈로그

### 4.1 ID 체계

`<축><번호>` 형식. 기술 백서 §8.5의 규칙별 기여도 측정을 위해 모든 규칙에 ID를 부여한다. **ID 없는 규칙은 추가하지 않는다** — 측정 불가능한 규칙은 제거 근거도 만들 수 없기 때문이다.

### 4.2 사다리

행동 전 통과 순서. 첫 통과 지점에서 멈춘다.

```
L1  추가 컨텍스트가 필요한가        → 아니면 즉시 실행
L2  최소 단위로 특정 가능한가       → 위치 검색 우선
L3  편집 범위가 확정되었는가        → 아니면 확정 먼저
L4  최소 패치로 가능한가            → 전체 재작성은 구조 변경 시만
```

L3이 THINK 축 우선 원칙의 집행 지점이다.

### 4.3 READ

> 파일 읽기는 입력 토큰의 최대 항목이며, 대부분의 읽기가 실제 필요 범위를 크게 초과한다. 이 축의 목표는 읽기를 줄이는 것이 아니라 **읽을 곳을 먼저 아는 것**이다.

| ID | 규칙 | 측정 핸들 |
|---|---|---|
| R1 | 파일을 열기 전에 검색으로 대상을 특정한다 | 읽기 직전 검색 호출 유무 |
| R2 | 확인된 범위만 읽는다. 전체 읽기는 구조 파악이 목적일 때만 | 범위 지정 읽기 비율 |
| R3 | 이미 읽은 파일을 다시 읽지 않는다. 편집 후 검증은 예외 | 동일 경로 중복 읽기 횟수 |
| R4 | 디렉터리 탐색은 필요한 깊이까지만 한다 | 트리 탐색 호출 수·깊이 |

### 4.4 WRITE

> 편집 방식이 출력 토큰과 이후 턴의 읽기 비용을 동시에 결정한다. 파일을 나누는 결정은 코드량이 아니라 **참조 hop 비용**으로 판단한다.

| ID | 규칙 | 측정 핸들 |
|---|---|---|
| W1 | 부분 치환을 우선한다. 전체 재작성은 구조 변경에 한정 | 전체 쓰기 : 부분 치환 비율 |
| W2 | 편집 앵커는 고유성이 확보되는 최소 폭으로 잡는다 | 앵커 불일치 실패 횟수 |
| W3 | 새 파일 생성보다 기존 파일 확장을 우선한다 | 신규 파일 생성 수 |
| W4 | 테스트·README·예제·설정은 요청받은 경우에만 만든다 | 요청 외 파일 생성 수 |
| W5 | diff로 확인 가능한 내용을 산문으로 다시 쓰지 않는다 | 응답 내 코드 블록 재게시 수 |

**W2는 양방향 지표다.** 앵커가 과도하게 좁으면 불일치가 늘고, 불일치 1회는 재읽기와 재시도를 부른다. 이 핸들이 증가하면 W2 자체를 완화해야 한다는 신호다. 규칙이 스스로를 감시하는 구조로, §9.1 IO 과긴축의 조기 경보로 쓴다.

**W5는 스타일 규칙이 아니다.** 중복 삭제 규칙이며 caveman의 정의역과 구분된다. 경계는 §4.6.

### 4.5 THINK

> 재시도 1회가 다른 축의 절감분 수십 회를 상쇄한다. 턴 수는 곱셈 계수이므로, 이 축은 다른 두 축보다 우선한다.

| ID | 규칙 | 측정 핸들 |
|---|---|---|
| T1 | 되돌리기 비용이 확인 비용보다 크면 확인을 먼저 한다 | 편집 되돌림·재편집 횟수 |
| T2 | 설계 선택이 남아 있으면 편집 전에 해소한다 | 동일 파일 연속 재편집 횟수 |
| T3 | 대상 코드의 현재 상태를 모르는 채로 편집하지 않는다 | 편집 실패율 |

**축 우선순위.** READ와 THINK가 충돌하면 THINK가 이긴다. T3이 R1~R3보다 상위이며, 이 순서를 SKILL.md 본문에 명시한다.

### 4.6 규칙 경계

각 규칙이 어디서 멈추는지를 명시한다. 이 경계가 없으면 §9.1과 §9.4가 발생한다.

| 규칙 | 적용 대상 | 비대상 |
|---|---|---|
| R2 | 특정 심볼·함수 확인 | 아키텍처 파악, 첫 진입 |
| R3 | 동일 세션 내 재조회 | 편집 후 검증, 외부 변경 후 |
| W1 | 국소 수정 | 파일 구조 변경, 대량 이동 |
| W4 | 산출물 자동 생성 | 사용자가 명시 요청한 경우 |
| W5 | diff로 보이는 변경 내용 | 설계 근거, 남은 선택지, 부작용, 사용자 판단 필요 사항 |
| T1 | 되돌리기 비용이 큰 편집 | 사소한 수정, 즉시 검증 가능한 변경 |

W5 행이 §9.4 설명 부족 위험의 차단선이다.

### 4.7 금지 조항

기술 백서 §7을 규칙 형태로 옮긴다.

```
X1  식별자를 축약하지 않는다
X2  의미를 보존한 채 표현을 압축하지 않는다
X3  관용구를 벗어난 표현을 쓰지 않는다
X4  한 줄에 로직을 결합하지 않는다
```

**규칙 문구에서 "토큰"을 직접 언급하지 않는다.** 기술 백서 §9.5에 따른 설계 결정이다. 각 규칙은 행동 수준으로 기술하고, 토큰은 결과 지표로만 존재한다. 에이전트에게 "토큰을 줄여라"라고 지시하는 순간 측정 밖 축으로의 전가가 시작된다.

### 4.8 불가침

```
어떤 규칙도 다음을 축소하지 않는다.
  신뢰 경계 검증 · 예외 처리 · 데이터 손실 방지 · 보안 · 접근성
```

Ponytail 승계. §7.4의 채택 게이트에서 별도 검증한다.

## 5. 트리거 평가셋

### 5.1 구성

`evals/trigger.json`. 최소 20문항, 양성 12 / 음성 8.

| 구분 | 유형 | 문항 수 |
|---|---|---|
| 양성 | 다중 파일 편집 | 3 |
| 양성 | 디버깅·원인 추적 | 3 |
| 양성 | 리팩터링 | 2 |
| 양성 | 코드베이스 탐색 | 2 |
| 양성 | 키워드 직접 언급 | 2 |
| 음성 | 비코딩 (산문·번역·일반 지식) | 4 |
| 음성 | 단발 1파일 편집 | 2 |
| 음성 | 골프·압축 요청 | 2 |

마지막 음성 2문항이 중요하다. "이 함수 최대한 짧게 줄여줘" 류에서 TEA가 발화하면 안 된다. §3.2 3문단의 효과를 직접 검증한다.

### 5.2 측정

문항당 3회 실행하여 발화율을 낸다. 60/40 분할로 학습·검증을 나누고, 문안 개선은 학습셋으로 하되 채택 판단은 검증셋 점수로 한다.

| 지표 | 목표 | 실패 시 |
|---|---|---|
| recall (양성 발화율) | ≥ 5/6 | 정의역 열거 확장 |
| precision (음성 미발화율) | ≥ 7/8 | 비적용 문구 강화 |

**주의.** 양성 문항은 에이전트가 자력으로 처리하기 어려운 수준이어야 한다. 단순 질의는 문안과 무관하게 발화하지 않으므로 평가 문항으로 무의미하다.

## 6. 벤치마크 절차

### 6.1 공통 조건

기술 백서 §8.3의 재사용 결정을 따른다.

```
대상   tiangolo/full-stack-fastapi-template
태스크 12개 feature 티켓
반복   n = 4
실행   headless 에이전트 세션
모델   2종 이상 (§9.3 대응)
```

### 6.2 3군 구성

| 군 | 구성 | 역할 |
|---|---|---|
| A | 스킬 없음 | 참조군 |
| B | Ponytail 단독 | **기준선** |
| C | Ponytail + TEA | 측정 대상 |

**순기여 = C − B.** A는 절감 규모의 상대 감각을 위한 참조이며 채택 판단에 쓰지 않는다.

B군 수치를 선행 공개치와 대조하여 재현성을 먼저 확인한다. 불일치 시 환경 문제를 배제한 뒤 C를 측정한다.

### 6.3 수집 항목

| 구분 | 항목 | 출처 |
|---|---|---|
| 주지표 | 총 토큰 (input + output + reasoning) | 실행 완료 통지 |
| 주지표 | 턴 수 | 세션 로그 |
| 부지표 | 재시도율, 도구 호출 실패율 | 세션 로그 |
| 부지표 | 규칙별 측정 핸들 12종 | 세션 로그 파싱 |
| 검증 | assertion 통과율 | 채점 |
| 검증 | 불가침 항목 유지 | 적대적 티어 |

**추론 토큰을 반드시 포함한다.** 이 항목을 빼면 §9.3의 사다리 비용 위험이 측정에서 사라진다.

토큰·시간 데이터는 실행 완료 통지 시점에만 확보되므로 즉시 저장한다.

### 6.4 규칙별 기여도

12개 측정 핸들을 세션 로그에서 집계하여 규칙별 준수 여부와 총 토큰의 상관을 본다. 전체 순효과가 양수여도 개별 음수 항목이 존재할 수 있으므로, 3단계에서 음수 규칙을 제거한다.

**규칙을 늘리는 것은 이 측정을 통과한 뒤에만 허용한다.**

## 7. 채택 게이트

### 7.1 조건

기술 백서 §8.4의 5개 조건을 판정 가능한 형태로 옮긴다.

| # | 조건 | 판정 |
|---|---|---|
| 1 | 기능 동등성 | assertion 통과율 C ≥ B |
| 2 | 총 토큰 감소 | mean(C) < mean(B), 차이 > 합성 표준편차 |
| 3 | 턴 수 비증가 | mean turns C ≤ mean turns B |
| 4 | 재시도율 비증가 | 편집 실패율·중복 읽기율 C ≤ B |
| 5 | 불가침 유지 | 적대적 티어 C = B = 100% |

**전부 충족해야 채택한다.** 2번 단독 통과는 채택 사유가 아니다. §9.5의 목적 함수 동형성 위험 때문에, 총 토큰만 보는 판정은 구조적으로 위험하다.

### 7.2 분산 처리

에이전트 실행은 분산이 크다. 표준편차가 델타보다 크면 결론을 내지 않고 반복을 늘린다. n=4는 최소값이며, 경계 사례에서는 증가시킨다.

### 7.3 모델 간 일관성

최소 2개 모델에서 측정한다. 한 모델에서만 통과하면 채택하지 않고, 어느 조건에서 역전되는지를 문서화한다. 선행 사례가 특정 추론 모델에서의 역전을 보고했으므로, 이 항목은 형식적 절차가 아니다.

### 7.4 불가침 검증

적대적 티어를 별도 구성한다. 선행 측정에서 단순 축약 지시가 안전 항목을 100%에서 95%로 떨어뜨린 반면 사다리 기반 접근은 유지했다. TEA는 사다리 기반이나 §4.7의 금지 조항이 축약 지시로 오독될 여지가 있으므로 직접 검증이 필요하다.

## 8. 4단계 전환 명세

1~3단계에서 구현하지 않으나, 1단계 산출물이 전환을 막지 않도록 사전에 정한다.

### 8.1 강도 체계

이름 은유를 여기서 회수한다.

```
/tea [light | standard | strong | off]
```

`standard`가 기본값. 강도는 규칙의 적용 범위를 조절하며 규칙 자체를 바꾸지 않는다.

| 강도 | 적용 |
|---|---|
| light | THINK 축만 |
| standard | 3축 전부, §4.6 경계 적용 |
| strong | 3축 전부, 경계를 좁게 해석 |

`light`가 THINK 단독인 것은 이 축이 §3.2 우선순위상 최상위이고 과긴축 위험이 가장 낮기 때문이다. 최소 구성이 가장 안전한 구성과 일치한다.

### 8.2 Ponytail 모드 연동

기본값은 종속이다. Ponytail 모드를 읽어 대응 강도를 따라간다.

| Ponytail | TEA 기본 |
|---|---|
| lite | light |
| full | standard |
| ultra | strong |
| off | standard 유지 |

감지는 `~/.config/ponytail/config.json` 또는 대응 환경 변수로 한다. 미설치 시 `standard` 고정, 그리고 §8.4의 스텁을 활성화한다.

독립 지정은 명시적 오버라이드로만 허용한다. 사용자가 강도 개념을 두 번 학습하지 않게 하고, 두 스킬이 엇갈린 강도로 걸리는 상황을 막는다.

### 8.3 서브에이전트 스코프

기술 백서 §11.2 항목 3의 해소안이다.

선행 사례는 서브에이전트에 룰셋을 주입하되 읽기 전용 탐색 에이전트를 제외하는 용례를 든다. 구현량을 줄이는 규칙은 탐색 에이전트에 무의미하기 때문이다.

**TEA는 반대다.** READ 축은 탐색 에이전트가 정확히 최대 소비원이므로, 그곳에 반드시 걸어야 한다.

| 서브에이전트 유형 | Ponytail | TEA |
|---|---|---|
| 탐색·검색 (읽기 전용) | 제외 권장 | **필수 주입** |
| 구현·편집 | 주입 | 주입 |

주입 축을 유형별로 다르게 한다. 탐색 에이전트에는 READ 축과 T3만 주입하고 WRITE 축은 제외한다. 편집 권한이 없는 에이전트에 편집 규칙을 넣는 것은 계층 2 예산 낭비다.

### 8.4 Ponytail 미설치 대응

기술 백서 §5.5의 스텁이다. 단일 규칙으로 제한한다.

```
P1  새 코드를 쓰기 전에 기존 코드·표준 라이브러리·플랫폼
    기본 기능으로 해결되는지 먼저 확인한다
```

**의도적으로 부실하다.** 계층 B는 TEA의 정의역이 아니며, 스텁의 목적은 대체가 아니라 최소한의 공백 방지다. Ponytail 병용을 권고 문구로 안내한다.

### 8.5 감사 커맨드

```
/tea-audit
```

세션 소비 **분포**를 보고한다. 총량과 비용은 caveman의 `/caveman-stats`가 이미 제공하므로 재구현하지 않는다.

출력 항목은 §4의 측정 핸들 12종이며, §6.4 기여도 측정과 같은 파서를 공유한다. 4단계 구현 시 벤치마크 파서를 재사용하므로 추가 비용이 낮다.

## 9. Schema-Hub 정합

### 9.1 분리 원칙

14섹션 포맷을 계층 2에 그대로 넣으면 §2.2 예산을 초과한다. 다음 기준으로 분리한다.

| 성격 | 배치 |
|---|---|
| 에이전트가 매 판단에 참조하는 내용 | 계층 2 (SKILL.md) |
| 사람이 읽거나 유지보수에 필요한 내용 | 계층 3 (`references/spec.md`) |
| 판단 사례·경계 예시 | 계층 3 (축별 파일) |

### 9.2 미확정

실제 14개 섹션 목록이 이 문서의 입력으로 필요하다. 섹션명을 받으면 위 기준으로 배치표를 확정한다. **하네스 팩 착수 전 유일한 외부 입력 의존 항목이다.**
