# Harness Expand Pack — TEA (Token Engineering for Agents)

에이전트 컨텍스트 IO 규율 스킬. 코드 문자 수가 아니라 **태스크 완료까지의 총 토큰과 턴 수**를 줄인다. Ponytail(구현량)·caveman(출력 표현)이 점유하지 않은 공백 — 어떻게 읽고 편집하고 판단하는가 — 이 정의역이다.

> 표기: `{{...}}` 는 진행 중 채운다. 백서는 `docs/`, 운영 규율은 `HARNESS.md`.

## 이 프로젝트의 특이점
일반 소프트웨어 프로젝트와 두 가지가 다르며, 게이트 설계가 여기서 갈린다.

- **산출물이 코드가 아니라 규칙 문서다.** 빌드·타입체크로 검증할 것이 없다. 대신 트리거 발화율과 3군 벤치마크가 게이트 역할을 한다.
- **개입이 역효과일 수 있다.** 규율을 잘못 걸면 총 토큰이 **늘어난다**. 선행 사례(caveman)가 실제로 그랬다. 따라서 "동작함"이 아니라 "기준선 대비 개선"만이 완료다.

## Phase 의존 순서
```
M0 스캐폴딩
 └ M1 description 확정 ★      ← 발화하지 않는 본문은 측정 불가. 반드시 선행
    └ M2 SKILL.md 본문
       └ M3 references
          └ M4 계측 하네스 ★
             └ M5 3군 벤치마크 ★
                └ M6 규칙 정제·채택 판정 ★
                   └ M7 플러그인 전환
                      └ M8 크로스 에이전트 (유보)
```
M1이 M2에 선행하는 이유는 설계 백서 §11의 결정이다. 발화가 보장되지 않으면 본문의 효과를 측정할 수 없다.

## 세션 프로토콜 (요약 — 상세는 `HARNESS.md` §0)
1. 시작: `CLAUDE.md`(자동) → 이 README → `PROGRESS.md` → 현재 `phases/Mn.md` → 관련 `docs/` 절.
2. 작업: 한 번에 한 phase. 작업 단위마다 그 phase의 검증 명령으로 게이트 확인.
3. 종료: `PROGRESS.md` 갱신(완료·증거·다음 할 일·미결·결정 링크) → 커밋.
